# Workflow: database migrations

Postgres (PostGIS 16) is the system of record; Redis is a rebuildable projection. A schema mistake is the most
expensive mistake you can ship, so this is the strictest workflow in the repo.

Related: vault note [`40-backend/migrations.md`](../../../40-backend/migrations.md) · the `/db-migrate` skill ·
[`docs/operations/recovery-runbook.md`](../../operations/recovery-runbook.md) section 6 ·
[`docs/remediation/stage-c-contract.md`](../../remediation/stage-c-contract.md) section 1.1 and 6.

## 1. How migrations work here

- **Hand-authored SQL**, numbered, in `apps/api/migrations/` (`0001_init.sql` … `0017_pool_member_agreed_fare.sql` at
  the time of writing). Not generated by `drizzle-kit`; do not commit `drizzle-kit generate` output.
- The Drizzle schema `apps/api/src/db/schema.ts` is what the application code reads through. **You edit both**: the
  SQL file is what runs, `schema.ts` is what TypeScript sees. Keep CHECK constraints, defaults and indexes mirrored.
  Constraint names that code needs to recognise are mapped in `apps/api/src/db/constraints.ts`
  (`pgConstraintViolation`), so name constraints explicitly.
- The runner `apps/api/src/migrate.ts`:
  1. connects with `DATABASE_URL`;
  2. takes a session-level Postgres **advisory lock** (key `726001011`) so a deploy racing a rollback or two
     operators serialise;
  3. creates `_rcab_migrations(id, name UNIQUE, ran_at)` if missing;
  4. lists `*.sql`, sorts **lexically**, skips names already recorded, and for each pending file sends the whole file
     as one multi-statement query, then records the filename.
  A multi-statement simple query is one implicit transaction in Postgres, so a failing statement rolls the whole file
  back and the name is not recorded (unless the file issues its own `COMMIT`; do not). The `INSERT` that records the name is a *separate* statement, so a crash between the two re-runs the file on the next start: this is why every migration must be re-runnable (known gap, recovery runbook section 8).
- **Never edit or rename an applied migration.** The runner keys on the filename; changed content is silently ignored
  on databases that already ran it, and breaks fresh ones differently. Fix forward with a new number.
- **Forward-only.** There are no down migrations. Production rollback ([release-and-deploy.md](release-and-deploy.md))
  re-deploys old images against the *new* schema, so a migration must be readable by the previous release.
- **When they run**
  - dev: **never automatically.** After `pnpm dev:up` on a fresh volume, or after pulling new migrations:
    `docker compose --env-file .env.dev -f infra/docker/docker-compose.dev.yml exec api npx tsx src/migrate.ts`
    (or `/db-migrate migrate`). `pnpm dev:down -v` wipes the volume.
  - integration tests: `@rcab/test-fixtures` `runMigrations` applies the same files to a fresh Testcontainers
    Postgres, so a bad migration fails `pnpm test:int` before CI.
  - production: a one-shot `migrator` service (`node dist/migrate.js`, same image as the api) runs before api/web
    start; `scripts/deploy/deploy.sh` runs it as a step and aborts the release (stack untouched) if it fails.

## 2. Authoring rules

1. **One migration = one logical change.** Backfills in a separate migration from the schema change when large.
2. **Idempotent and additive by default:** `CREATE TABLE/INDEX IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`,
   `DROP TRIGGER IF EXISTS` + `CREATE`, `CREATE OR REPLACE FUNCTION`. Constraints that accept existing rows.
3. **Expand -> migrate -> contract.** Add nullable, ship code that writes both, backfill, then tighten in a later
   release. Never rename; add the new column and deprecate the old (0017 keeps the legacy `quoted_fare_cents` beside
   `agreed_fare_cents`).
4. **Destructive statements are a HITL stop** (`DROP COLUMN/TABLE`, type narrowing, `NOT NULL` on a populated column):
   flag them to the owner before applying anywhere. The vault rule is no drops in Phase-0 without a follow-up ADR
   (ADRs are also a HITL area).
5. **Guarantees belong in the database.** The Stage C migrations put the invariants in constraints and triggers
   (one guard per driver, seat counts derived by trigger, member only joins an open pool, state version bump), so
   a bug in application code cannot corrupt state. Prefer that over comments.
6. **Do not guess at legacy data.** If a migration cannot mechanically repair a row (a driver with two active trips,
   an orphan pool member), record it in `migration_conflict` (unique per `(migration, kind, subject)`) and leave a
   human to decide. 0014 and 0016 are the pattern to copy.
7. **Document the migration in its header comment** (why, what it guarantees, how legacy rows are treated, who
   decided). Mirror the change in `schema.ts` and in the vault schema note (`40-backend/schema-postgres.md`,
   `30-domain/data-model.md`).

## 3. Step by step: add a migration

```bash
# 1. next number: highest existing prefix + 1, snake_case slug
ls apps/api/migrations | tail -3
# 2. write apps/api/migrations/00NN_<slug>.sql ; mirror it in apps/api/src/db/schema.ts
# 3. apply to dev and look at it
DC="docker compose --env-file .env.dev -f infra/docker/docker-compose.dev.yml"
$DC exec -T api npx tsx src/migrate.ts
$DC exec -T postgres psql -U rcab -d rcab -c "\d rides"
# 4. run the migration a second time: it must be a no-op (the runner skips it; also run the SQL by hand once to prove idempotency)
# 5. tests: pnpm --filter @rcab/api test ; pnpm test:int
```

Add an integration test for every new invariant using **independent connections** (see
[testing.md](testing.md) race patterns). If the migration changes data on existing rows, add an *upgrade-path* test
in the style of T36 in `apps/api/test/integration/migrations-stage-c.int.spec.ts`: create a scratch database,
migrate it to N-1, seed legacy state (including the ugly cases), migrate to N, assert the result and the recorded
conflicts.

## 4. Rehearse on a copy of real data before production

Required for any migration that rewrites or constrains existing rows. Never rehearse against the live database.

```bash
# a) get a copy: a restored backup (see restore-drill) or a dump of the dev DB
$DC exec -T postgres pg_dump -U rcab -Fc rcab > "$TMPDIR/rcab.dump"

# b) scratch Postgres (same image as the stack) on a spare port
docker run -d --name rcab-mig-rehearsal -e POSTGRES_PASSWORD=rehearsal -p 55499:5432 postgis/postgis:16-3.4
# wait for pg_isready, then:
docker exec rcab-mig-rehearsal createdb -U postgres rcab
docker exec -i rcab-mig-rehearsal pg_restore -U postgres -d rcab --no-owner < "$TMPDIR/rcab.dump"

# c) apply the pending migrations to the copy
cd apps/api && DATABASE_URL=postgres://postgres:rehearsal@localhost:55499/rcab npx tsx src/migrate.ts

# d) check: new objects exist, row counts unchanged, invariant SQL returns zero rows,
#    and `SELECT * FROM migration_conflict WHERE resolved_at IS NULL` is what you expect
# e) clean up
docker rm -f rcab-mig-rehearsal
```

For a copy of *production* data use `scripts/recovery/restore-drill.sh` (it restores the newest encrypted backup into a
throwaway Postgres, verifies migrations are current and runs invariants I1–I9, and never touches the live stack);
see [incident-and-recovery.md](incident-and-recovery.md). `scripts/deploy/rehearse-local.sh` rehearses a whole
release/rollback against a throwaway compose project.

Take a fresh backup before any production migration that rewrites data (the runbook section 2 explains what the
backup is and what RPO you actually get).

## 5. When a migration reports `migration_conflict` rows

Some migrations deliberately do not repair ambiguous legacy rows; they write them to `migration_conflict` and move
on. Until a human resolves them, the affected driver or pool runs *without* the new protection, and the audit
invariants report them.

```sql
SELECT id, migration, kind, subject, detail, detected_at
  FROM migration_conflict WHERE resolved_at IS NULL ORDER BY id;
```

| `kind` | From | What it means | Resolution |
|---|---|---|---|
| `driver_multiple_active_trips` | 0014 | A driver held more than one active trip (pre-Stage-C double-assignment bug); no guard row was created | A person chooses the single trip to keep. Then `psql -v ON_ERROR_STOP=1 -v driver_id=… -v keep_kind=solo\|shared -v keep_trip=… -v drop_trip=… -f scripts/recovery/resolve-driver-conflict.sql` (one transaction, asserts first). Never cancel a pool by SQL. |
| `assignment_unknown_driver` | 0014 | An active trip names a driver id with no `driver` row | Restore the driver then add the guard, or cancel the trip with the same `UPDATE`; never invent a driver |
| `passenger_multiple_active_pools` and other `pool_*` | 0016 | Membership/capacity problems when moving jsonb members to `pool_member` (newest membership kept active; older ones deactivated but recorded) | Read `detail`; fix the cause; `UPDATE migration_conflict SET resolved_at = now(), resolution = '…' WHERE id = …` |

The full procedure with the exact statements, rules and the rehearsal record is
[runbook section 6](../../operations/recovery-runbook.md). Mark a row resolved with a sentence that says what you
decided; that sentence is the audit trail. Rows are never deleted.

## 6. Pitfalls seen in this repo

- Forgetting the explicit `migrate` step after pulling: the api boots but queries fail on missing columns.
- Editing `schema.ts` without the SQL (or vice versa): types lie, or the runtime breaks. Tests catch the second
  (they run real SQL) but not always the first.
- A trigger-driven `UPDATE` interacting with a table-wide `NOT NULL`/`CHECK ... NOT VALID` on legacy rows (see the
  comment in 0017 for why `agreed_fare_cents` is nullable with a `BEFORE INSERT` guard instead).
- Adding a column with a volatile default on a large table (rewrites the table). Add nullable, backfill in batches.
- Assuming production applies migrations before the *old* api stops: the old release runs against the new schema
  for a moment, and again after an automatic rollback. Additive changes only.
