Where it stands

Production is reached one runnable demo at a time. Each demo is a hard waypoint — docker up, tests green, developer walks it, signs off. A demo is not done because the code merged; it is done when a human has walked it.

The gap this runbook exists to close Demos 0 and 1 were walked by hand on 2026-06-15 and produced eight real bug fixes. Demos 2–5 have shipped code, merged PRs and green integration tests, but no human has walked them end to end. Until someone does, "E1–E6 done" means "the tests we wrote pass", not "the product works".

Read this first

Six facts about this stack that cost hours if you learn them the hard way. Every one has burned a prior session.

Ports are not the obvious ones
Web is :3002, Grafana is :3001 — they are easy to swap in your head. Postgres publishes :55432, not 5432, because 5432 is usually a locally-installed Postgres.
OSRM has no host port
Neither do Loki or Alertmanager. They live only on rcab_dev_net. localhost:5000 and localhost:3100 refuse the connection — that is correct behaviour, not a broken container. Reach OSRM from inside: docker compose … exec -T api sh -c 'curl http://osrm:5000/…'.
Driver presence expires in 60 seconds
The API auto-offline sweep runs every 15 s and drops any driver whose driver:state:<id>.last_seen is older than 60 s. A seeded driver that never heartbeats vanishes from active_drivers about a minute later. Hold them online with ./scripts/seed-dev.sh --keepalive.
Migrations are never applied automatically
Not on dev:up, not on container restart. Eleven hand-authored SQL files in apps/api/migrations/ (0001…0011_rides_scheduled.sql) applied in order by src/migrate.ts, which tracks what it has run in _rcab_migrations. Forgetting this looks like "the scheduled columns don't exist".
All coordinates must be near Guwahati
The dev OSRM graph is NE-India only, centred around 26.1445, 91.7362. A pickup outside it returns no route, so quotes fail and dispatch never starts. Set your emulator GPS inside the region too.
Seeded users cannot sign in
seed-dev.sh upserts fixture drivers, clients and vehicles and puts drivers in the geo index — good for watching dispatch fan out. But their firebase_uids are synthetic, so they cannot complete phone OTP and they never answer an offer. Accepting a ride still needs a real driver on the Flutter app.

Skipping SMS during a walk Add test phone numbers with fixed codes in the Firebase console (Authentication → Sign-in method → Phone → Test numbers). The prior pass used +919999999999 / 123456. For curl-only checks, FIREBASE_PHONE_TEST_TOKEN in .env.dev is a pre-minted ID token.

Bring-up

Four commands to a running stack, one to prove it, one to load the schema. First run builds the OSRM routing graph and takes several minutes.

1 · Start everything

pnpm dev:up      # compose up -d --build; creates .env.dev on first run; includes obs profile
pnpm dev:smoke   # polls api / until postgres + redis report connected → 200
pnpm dev:logs    # follow
pnpm dev:down    # stop + remove. add -v to wipe volumes for a clean slate

The :slim variants (dev:up:slim, dev:down:slim) skip the observability containers when you do not need Grafana.

2 · Verify each service by hand

curl -s localhost:3000/v1/health/live  | jq   # {"ok":true}
curl -s localhost:3000/v1/health/ready | jq   # postgres/redis/osrm all ok
curl -s localhost:3000/metrics | head         # prometheus text format

# OSRM is network-internal — go through the api container:
docker compose --env-file .env.dev -f infra/docker/docker-compose.dev.yml exec -T api \
  sh -c 'curl -s "http://osrm:5000/route/v1/driving/91.7362,26.1445;91.7898,26.1758"' | jq .code
# → "Ok"

open http://localhost:3002   # web app
open http://localhost:3001   # Grafana (admin/admin)
open http://localhost:3003   # Uptime-Kuma

Or one shot: /smoke-check.

3 · Apply migrations — once per fresh database

docker compose --env-file .env.dev -f infra/docker/docker-compose.dev.yml \
  exec api npx tsx src/migrate.ts
# expect: [migrator] applied 00xx_*.sql … [migrator] done

# confirm the scheduled columns landed:
docker compose --env-file .env.dev -f infra/docker/docker-compose.dev.yml exec -T postgres \
  psql -U rcab -d rcab -c "\d rides" | grep -E 'type|scheduled_for'

Or /db-migrate, which previews the pending SQL before applying it.

4 · Fixture data

./scripts/seed-dev.sh --reset --drivers 5 --keepalive
# upserts drivers/clients/vehicles, puts drivers in the Guwahati geo index,
# and heartbeats them so the 60 s sweep doesn't drop them

5 · Driver app — outside compose

cd apps/driver-app
flutter pub get
flutter run   # point its API config at your laptop's LAN IP, never localhost

Grafana renders empty until traffic exists http_request_duration_seconds_count, rcab_dispatch_* and rcab_active_drivers have zero series until something exercises the API. To wake the Overview dashboard before a demo: for i in $(seq 1 200); do curl -s localhost:3000/v1/health/live >/dev/null; done

Epic E2 — Auth & identity · web

I am a real user

ProvesPhone-OTP signup, first-party JWT issuance, silent refresh, and logout revocation.

  1. Open http://localhost:3002/signin.
  2. Enter a Firebase test phone number, let the invisible reCAPTCHA resolve, Send OTP.
  3. Enter the fixed test code → Verify → you land on /book signed in as a client.
  4. DevTools → Application → Cookies: rcab_refresh is HttpOnly and SameSite.
  5. Check the row landed exactly once: 
    docker compose … exec -T postgres psql -U rcab -d rcab -c \
  "SELECT id, phone_e164, role FROM app_user ORDER BY created_at DESC LIMIT 5;"
  6. Hard-refresh → still signed in (that is the refresh path). Sign out → cookie cleared, and a stale access token now returns 401.

Curl-only variant

curl -s localhost:3000/v1/auth/firebase-exchange -H 'Content-Type: application/json' \
  -d "{\"id_token\":\"$FIREBASE_PHONE_TEST_TOKEN\"}" | jq
# → {access_token, user}. Reuse that token as Authorization: Bearer … below.

Epic E3 — Driver presence · Flutter app

The driver is online

ProvesA driver signs in, registers a vehicle, goes online, and streams location into the Redis geo index.

  1. Launch the driver app. Sign in with a driver test phone number.
  2. Register a vehicle — type, registration number, seats → POST /v1/vehicles.
  3. Toggle Online → POST /v1/drivers/online. A foreground-service notification appears.
  4. The app streams driver:location over the websocket. Confirm presence: 
    docker compose … exec -T redis redis-cli ZRANGE active_drivers 0 -1 WITHSCORES
docker compose … exec -T redis redis-cli HGETALL driver:state:<driver-user-id>
    Or /redis-inspect. Move the emulator GPS — scores update at roughly 1 Hz behind a 3 s geo throttle.
  5. Toggle Offline → the driver leaves active_drivers.

Common missEmulator GPS parked outside the Guwahati graph area. The driver appears in Redis but no ride will ever route to them.

Epic E4 — Normal booking · web + driver app

Book a normal ride

ProvesThe whole spine: quote → request → top-K dispatch → accept → drive the state machine → complete → rate.

Setup: a client signed in on web (Demo 1) and a driver online near the pickup (Demo 2), both inside the Guwahati graph.

  1. Web /book: pick pickup and drop on the Leaflet map. A live quote shows fare and ETA (POST /v1/rides/quote).
  2. Book → POST /v1/rides with type=normal and an Idempotency-Key. The ride persists as requested, then dispatch fans out.
  3. Driver app shows a ringing offer card (ride_offer) with a countdown → Accept (ride_offer_response{accept:true}). Ride → accepted; web flips to live tracking.
  4. Driver drives the machine via POST /v1/rides/:id/state: en_route → arrived → start → complete. Web shows the driver marker moving (driver_location, 1 Hz) and the banner updating (ride_state_changed).
  5. On completed, both sides get a rating prompt → submit stars (POST /v1/rides/:id/ratings).

Watch it while it runs

docker compose … exec -T postgres psql -U rcab -d rcab -c \
  "SELECT id,status,type,driver_id,fare_cents FROM rides ORDER BY created_at DESC LIMIT 3;"
/redis-inspect   # claim:ride:*, offer:*, bull:dispatch:* during dispatch

No-driver path: with nobody online, dispatch exhausts wave 2 and the ride lands on no_driver with the client notified.

Epic E5 — Shared booking

Shared works

ProvesTwo clients on overlapping corridors pool into a single ride with an ordered multi-stop sequence and per-seat pricing.

Setup: two or more clients, at least one online driver, routes that genuinely overlap in Guwahati.

  1. Client A books with Share selected (POST /v1/rides, type=shared) → opens a pool.
  2. Client B books a similar route. Matching scores it against A's open pool on route similarity over cached OSRM polylines and slots B in — pool:update fans out and the seat count ticks. Inspect with /pool-inspect.
  3. The pool closes (seats full, or timeout) → shared dispatch offers the driver the multi-stop sequence, readable at GET /v1/rides/:id/stops.
  4. Driver confirms stops in order (stop:pickup_confirmed / stop:drop_confirmed). The UI must refuse a drop before its matching pickup.
  5. Compare fares: each passenger's shared fare is below their solo fare.

Pass criteria

Epic E6 — Scheduled booking · sign-off owed

Scheduled works

ProvesA future booking sits idle, wakes ten minutes before pickup, and then runs the ordinary dispatch path. Cancelling before the wake is free and drops the job.

  1. Quote as normal (POST /v1/rides/quote, type=scheduled).
  2. Request with a scheduledFor between 15 minutes and 24 hours out: 
    curl -s localhost:3000/v1/rides -X POST -H "Authorization: Bearer $ACCESS" \
  -H 'Content-Type: application/json' -H "Idempotency-Key: $(uuidgen)" \
  -d '{"type":"scheduled","originLat":26.1445,"originLng":91.7362,
       "destLat":26.1758,"destLng":91.7898,"quoteToken":"<from quote>",
       "scheduledFor":"<ISO, 20 min from now>"}' | jq
    The ride persists requested with type=scheduled and no dispatch happens. A delayed job is queued: 
    docker compose … exec -T redis redis-cli KEYS 'bull:scheduled-dispatch:*'
  3. Wake: at scheduledFor − 10 min the job fires, emits ride.requested, and the identical Demo 3 dispatch path runs. To demo quickly, set scheduledFor about 16 minutes out, or lower SCHEDULED_WAKE_LEAD_MS in .env.dev and restart the api.
  4. Cancel before wake (POST /v1/rides/:id/cancel) → the ride becomes cancelled and the delayed job is dropped. Confirm the bull:scheduled-dispatch:* key is gone.
  5. Window guard: a scheduledFor under 15 minutes or over 24 hours returns 400 scheduled_for_out_of_window.

Ride state machine

requested→ dispatching→ accepted→ en_route→ arrived→ in_progress→ completed
from dispatching, if every wave is exhausted →no_driver
from any pre-complete state →cancelled·no_show

The driver drives forward transitions through POST /v1/rides/:id/state, guarded by SELECT … FOR UPDATE. Cancellation is role-aware, and Phase-0 charges no cancellation fee.

Where state lives

Nine Postgres tables hold anything durable. Anything in-flight — offers, claims, pools, queues, presence — lives in Redis and disappears with it.

StoreKey or tableHolds
Postgresapp_user · client · driver · vehicleIdentity and profiles. One user row per phone; role is client or driver
PostgresridesSolo, shared and scheduled rides — status, type, scheduled_for, fare, unique idempotency_key, lifecycle timestamps
Postgresshared_rides · ride_stopsPool seat counts, members, and the ordered stop sequence
PostgresratingsTwo-sided stars, unique per direction. Capture only — aggregation is E7
Postgresauth_refresh_tokenRefresh tokens. Revocation is revoked_at here — not in Redis
Redisactive_drivers (GEO ZSET)Online driver positions — the dispatch candidate source
Redisdriver:state:<id> (HASH)Availability, current_ride_id, last_seen
Redisclaim:ride:<id>SET NX lock that makes first-accept-wins atomic
Redisoffer:list:* · offer:type:* · ride:<id>:offeredOutstanding dispatch offers
Redispool:<rideId> + :seatsShared pool state; seat allocation is an atomic Lua script
Redisidem:rides:<key>Idempotency key → ride id, 24 h
Redisbull:dispatch:* · bull:matching:* · bull:scheduled-dispatch:*Wave timeouts, hard-fail, pool expiry, scheduled wake jobs

API surface

22 routes, all under /v1 except / and /metrics. Auth is a first-party JWT via Authorization: Bearer, except the public health and auth-entry routes; POST /v1/auth/refresh is additionally CSRF-guarded by an Origin check. Dispatch has no HTTP surface — it is entirely event and queue driven, which is why you inspect it through Redis rather than curl.

Config worth knowing

.env.dev is created by pnpm dev:up. Validate yours with /env-validate. The variables that change demo behaviour: SCHEDULED_WAKE_LEAD_MS (how far ahead a scheduled ride wakes), MATCHING_POOL_TIMEOUT_MS (how long a shared pool stays open), SCHEDULED_DISPATCH_CONCURRENCY, OSM_PBF_URL (the OSRM region), FIREBASE_PHONE_TEST_TOKEN, and JWT_SECRET.

Open follow-ups from the last manual pass

  • No apps/web/.env.example. The four NEXT_PUBLIC_FIREBASE_* keys are undocumented, so a fresh clone cannot sign in until someone pastes a Firebase config by hand.
  • The api dev transform drops decorator metadata. tsx uses esbuild, which does not emit design:paramtypes, so NestJS silently injects undefined into implicit constructor params. The auth controller and service work around it with explicit @Inject. A real fix means swc with decoratorMetadata, or tsc --watch. If you see Cannot read properties of undefined (reading '<method>') in a new provider, this is why.
  • pnpm dev:up does not detect lockfile drift against the anonymous node_modules volumes. A newly added web dependency can be missing inside a running container even though the host installed it.
  • Rare integration flake, roughly 1 in 18 runs, unrelated to the fixed teardown issue — suspected Math.random() collisions on phone_e164 / reg_no in the seed helpers hitting unique constraints.
  • seedPilotCity in @rcab/test-fixtures is an empty stub.

Scope boundaryPhase 0 is one VPS and one docker-compose, per ADR-0009. Multi-host, Kubernetes and managed cloud services are out of scope — if a task seems to need them, that is an impact-analysis trigger, not a design decision to make on the spot.
